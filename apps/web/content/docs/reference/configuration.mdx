## File resolution

Unless you pass `--config <path>`, docker-doctor looks for the first of these, in order, in the scanned directory:

1. `docker-doctor.config.ts`
2. `docker-doctor.config.js`
3. `docker-doctor.config.mjs`
4. `docker-doctor.config.cjs`
5. `docker-doctor.config.json`
6. `docker-doctor.config.yaml`
7. `docker-doctor.config.yml`
8. a `"dockerDoctor"` key in `package.json`

If none of these exist, docker-doctor runs with its built-in defaults.

The `.ts` form relies on Node.js importing TypeScript directly, which it does by default from 22.18 on. That version is the CLI's supported floor. On an older runtime docker-doctor exits with a message pointing here, so use the YAML or JSON form instead.

```bash
npx @docker-doctor/cli@latest . --config ./custom-docker-doctor.config.ts
```

The path is resolved from the directory you run the command in, not from `[dir]`. Earlier releases resolved it from the scanned directory; that still works with a warning on stderr.

## Shape

```ts
// docker-doctor.config.ts
export default {
  rules: {
    "docker-doctor/no-root-user": "error",
  },
  categories: {
    "Image Size": "off",
  },
  ignore: {
    files: ["examples/**/Dockerfile"],
  },
};
```

| Key | Type | Purpose |
| --- | --- | --- |
| `rules` | `Record<string, "error" \| "warning" \| "info" \| "off">` | Override the severity of an individual rule by its full key |
| `categories` | `Record<Category, "error" \| "warning" \| "info" \| "off">` | Override every rule in a category at once. `"off"` drops all diagnostics in that category |
| `ignore.files` | `string[]` | Glob patterns for files to exclude from scanning |

The five valid `categories` keys are `Security`, `Performance`, `Best Practices`, `Compose`, and `Image Size`.

`ignore.files` patterns match paths relative to the scan root: `**` crosses directories, while `*` and `?` stay within one path segment. Brace expansion and character classes are not supported. A pattern that ends in `/` ignores the whole directory, so `vendor/` means `vendor/**`. A leading `./` has no effect. docker-doctor drops ignored files from discovery, so they produce no diagnostics and don't appear in the report's `project` lists.

docker-doctor never descends into version-control, dependency and cache directories (`.git`, `node_modules`, `.venv`, `coverage`, `dist`, `.next`, `.turbo` and similar). It also prunes directories matched by `ignore.files` before walking them: a pattern ending in `/**`, such as `examples/**`, skips the whole tree. Directories the current user cannot read are skipped with a warning on stderr instead of failing the scan. `build/`, `out/`, `target/` and `vendor/` are scanned because projects do keep real Dockerfiles there, so add them to `ignore.files` if yours are vendored.

## Inline ignore comments

To silence one finding, write a comment at the line it points to. The finding leaves `diagnostics` and appears in the `suppressed` list of the [JSON report](/docs/reference/cli#json-report), so the report still shows what was hidden. A suppressed finding counts toward neither the score nor the exit code.

```dockerfile
# docker-doctor-ignore no-secrets-in-env -- local-only placeholder, never deployed
ENV DB_PASSWORD=hunter2
```

```yaml
services:
  agent:
    privileged: true # docker-doctor-ignore no-privileged-service -- builds nested containers in CI
```

The comment has this form.

```text
# docker-doctor-ignore <rule>[, <rule>...] [-- <reason>]
# docker-doctor-ignore-file <rule>[, <rule>...] [-- <reason>]
```

- Name at least one rule, by its full key (`docker-doctor/no-root-user`) or its short name (`no-root-user`). There is no wildcard.
- The reason after `--` is optional. `--verbose` prints it, and the report stores it in `suppressed[].reason`.
- The first form covers one location. The `-file` form covers every finding of those rules in the file, including findings that have no line.
- A rule name docker-doctor does not know prints a warning with the file and line on stderr. The other names in the same comment still apply. A comment with no rule name prints a warning and does nothing.
- `--no-config` also ignores these comments. A comment in a repository you did not write is as author-controlled as its config file.

### In a Dockerfile

A comment applies to the next instruction. It suppresses findings reported on that instruction's first line. Several comments in a row all apply to the same instruction. A comment inside a multi-line instruction, between two `\` continuation lines, does nothing and prints a warning.

A `#` line inside a heredoc body is shell, not a comment.

The `-file` form must sit in the comment block at the top of the file, below any parser directives such as `# syntax=`. Put it anywhere else and docker-doctor warns and does nothing. The order matters because BuildKit ends its parser directive block at the first comment that is not a directive. A comment above `# syntax=` turns that line into an ordinary comment, so the build silently loses its frontend. For the same reason, docker-doctor honors no ignore comment, in either form, above a parser directive.

```dockerfile
# syntax=docker/dockerfile:1
# docker-doctor-ignore-file require-labels -- labels come from the build pipeline
FROM node:22.2.0-alpine
```

The line a finding points to decides which instruction the comment must sit above. Run `docker-doctor --verbose` to see it. Rules that judge a whole Dockerfile report at a fixed place.

| Rule | Reports at |
| --- | --- |
| [`no-root-user`](/docs/reference/rules/no-root-user) | The last `USER` or `FROM`, whichever leaves the final stage as root |
| [`use-multi-stage`](/docs/reference/rules/use-multi-stage) | The `FROM` |
| [`require-healthcheck`](/docs/reference/rules/require-healthcheck), [`require-labels`](/docs/reference/rules/require-labels), [`use-dockerignore`](/docs/reference/rules/use-dockerignore) | Line 1 of the file, whatever it holds |

A comment above `CMD` can never suppress a finding reported at `FROM`. A comment can never sit above line 1, so the three rules in the last row take the `-file` form.

### In a Compose file

A comment that trails a line applies to that line. A comment on its own line applies to the next line that holds content, skipping blank lines and other comments. Both match a finding by its `line`. The `-file` form works as in a Dockerfile and must sit in the comment block at the top of the file.

Findings on keys that come from a YAML merge key (`<<: *base`) have no line, so only the `-file` form can suppress them.

A `#` inside a block scalar or a quoted string is text, not a comment.

## YAML and JSON configs

If you'd rather stay in YAML (you're writing Compose files anyway), the same shape works as `docker-doctor.config.yaml` — no `package.json` or `"type": "module"` required:

```yaml
# yaml-language-server: $schema=https://docker-doctor.vercel.app/schema.json
rules:
  "docker-doctor/no-root-user": error
categories:
  "Image Size": "off"
ignore:
  files:
    - "examples/**/Dockerfile"
```

The `yaml-language-server` comment gives you autocomplete and validation in editors with the YAML extension. JSON configs get the same via a `$schema` key:

```json
{
  "$schema": "https://docker-doctor.vercel.app/schema.json",
  "rules": {
    "docker-doctor/no-root-user": "error"
  }
}
```

The schema at [`/schema.json`](https://docker-doctor.vercel.app/schema.json) is generated from the built-in rule set, so every rule key and category autocompletes with its description.

## Typed config

`@docker-doctor/cli` exports the `DockerDoctorConfig` type and a `defineConfig` helper. Which one to use depends on how you run docker-doctor:

**Running via `npx` without installing** — use the type with `satisfies`. Type-only imports are erased when the config loads, so nothing needs to be installed at runtime (install `@docker-doctor/cli` as a devDependency if you want editor autocomplete):

```ts
// docker-doctor.config.ts
import type { DockerDoctorConfig } from "@docker-doctor/cli";

export default {
  rules: {
    "docker-doctor/no-root-user": "error",
  },
} satisfies DockerDoctorConfig;
```

**`@docker-doctor/cli` installed as a devDependency** — `defineConfig` also works and gives the same autocomplete:

```ts
// docker-doctor.config.ts
import { defineConfig } from "@docker-doctor/cli";

export default defineConfig({
  categories: {
    "Image Size": "off",
  },
});
```

`defineConfig` is a real runtime import — a config that uses it fails to load when the package isn't installed in the project, so prefer the `satisfies` form for npx-only projects.

docker-doctor reports unknown rule keys and unknown category names on stderr (`Warning: Unknown rule "…" in config`, `Warning: Unknown category "…" in config`), so a typo in a rule or category name doesn't go unnoticed. It drops unknown top-level keys without a warning. An invalid severity throws a config error that names the rule or category.
